Front Matter

Abstract

This report presents the Pharmacy Tracking System, a modern desktop application built with Java 17, Java Swing (FlatLaf), and MySQL. The system addresses inventory management problems common in small pharmacies that still rely on paper records or spreadsheets, particularly in resource-constrained environments where enterprise software is unaffordable or requires infrastructure that is unavailable.

The application covers six functional areas: role-based access control with three user roles (Admin, Pharmacist, Technician); complete medicine inventory management with batch tracking, therapeutic categories, and configurable reorder thresholds; a billing engine that records every sale and updates stock in real time; a demand forecasting module using a 30-day Simple Moving Average to project the next seven days of demand per medicine; a purchase order workflow with transactional stock receiving that uses database transactions to guarantee data consistency; and a live dashboard showing low-stock alerts, near-expiry warnings, and total inventory value on every login.

The system initializes its own database schema on first launch on a local MySQL instance with no manual setup required. All major use cases were validated through structured manual testing. A security review identified four vulnerabilities that are documented with concrete remediation steps.

Keywords: pharmacy management, inventory control, demand forecasting, Simple Moving Average, role-based access control, Java Swing, FlatLaf, MySQL, healthcare informatics.

Chapter 1

Introduction

1.1 Background

Many community pharmacies in West Africa and similar developing-world settings still manage inventory with paper ledgers or basic spreadsheets. The consequences are predictable: medicines run out without warning, expired stock stays on shelves, and there is no record of who changed what. A stockout of a critical antibiotic or an undetected expired batch can directly affect patient health and safety.

Enterprise pharmacy software exists but targets large hospital chains with full IT departments and five-figure annual budgets. A small independent pharmacy does not have those resources. This project builds a practical tool that fits that context: it works offline, installs without a database administrator, and can be operated by pharmacy staff with minimal technical training.

1.2 Problem Statement

Manual pharmacy management has four specific weaknesses. There is no real-time view of stock, so shortages are only discovered when a customer asks for something unavailable. Expiry dates are not monitored systematically, which risks dispensing expired medicines. Purchasing decisions rely on guesswork rather than sales history. And there are no access controls, meaning any staff member can modify or delete records without accountability.

1.3 Objectives

  1. Build a multi-module desktop application in Java that covers the full pharmacy workflow.
  2. Implement role-based login with three permission levels: Admin, Pharmacist, and Technician.
  3. Provide full inventory management including batch numbers, therapeutic categories, and per-medicine reorder thresholds.
  4. Build a demand forecasting engine using a 30-day Simple Moving Average to project seven-day demand.
  5. Add a purchase order and stock-receiving workflow using proper database transactions.
  6. Show all critical alerts on a single dashboard visible immediately after login.
  7. Make the application self-configuring so it creates its own database schema on first launch.

1.4 Scope

This version is designed for a single pharmacy location. It does not include barcode scanning, prescription tracking, insurance billing, or remote web access. These are noted as future work in Chapter 9. The forecasting algorithm is intentionally simple so the logic is transparent and easy to verify without a data science background.

Chapter 2

Literature Review

2.1 Pharmacy Management Systems

Pharmacy information systems have been in use in hospitals in North America and Europe since the 1980s. Modern commercial platforms such as ScriptPro and PioneerRx offer e-prescribing integration, DEA compliance reporting, and full patient medication history. These tools cost tens of thousands of dollars per year and require dedicated server infrastructure and IT support, making them inaccessible for small independent pharmacies.

A 2020 survey of 120 community pharmacies in Lagos found that 73 percent still used handwritten ledgers. A related study in Dakar in 2022 found similar patterns, identifying cost, unreliable electricity, and lack of technical staff as the main barriers to digital adoption. These findings shaped the design decisions in this project: a low-cost local MySQL database that runs on any standard PC, operation without internet connectivity after initial setup, and a graphical interface simple enough for non-technical staff to learn quickly.

2.2 Inventory Control Methods

Three standard models appear in the inventory management literature. The Economic Order Quantity model minimises total cost by balancing ordering and holding costs. The Reorder Point method triggers a purchase order when stock falls below a fixed threshold. Just-in-Time minimises held inventory by matching deliveries to actual consumption rates.

For pharmacies with stable dispensing patterns, the Reorder Point model is the most practical. This system implements it directly: each medicine has a configurable threshold, and an alert fires when current quantity falls at or below that value, or when the forecasting engine predicts the stock will be exhausted within seven days. Both conditions are checked simultaneously so the alert arrives before the pharmacy runs out, not after.

2.3 Demand Forecasting

A 2019 study compared Simple Moving Average, Exponential Weighted Moving Average, and ARIMA models across 50 generic medicines in an Indian district hospital. SMA with a 28-to-35-day window came within 8 percent of ARIMA accuracy on mean absolute percentage error while being far simpler to implement, audit, and explain to non-technical stakeholders. That result directly supports the choice of a 30-day SMA for this project.

Chapter 4

Architecture and Design

4.1 System Architecture

The application uses a two-tier architecture with a deliberate internal separation between the user interface and all data access logic. Swing frame classes handle display, user input, and navigation. Two helper classes centralise all business logic and database operations. No SQL statements or JDBC calls appear inside any frame class. This separation means that changing a database query affects one place in the codebase, and adding a new frame requires no changes to the database layer.

Figure 1: Three-tier system architecture showing all eleven classes organised by layer.

Presentation Layer: Eight Swing JFrame classes handle user interaction. Each frame is responsible for exactly one module of the system.

Business Logic Layer: DatabaseHelper centralises all JDBC connections, schema creation, and result set conversion. ForecastingHelper runs the SMA algorithm, identifies alerts, and calculates inventory value. Neither class has any UI code.

Data Layer: MySQL 8.x running as a local server instance. Five tables store all persistent state. The schema is automatically initialised on first launch via the DatabaseHelper class.

Chapter 5

Database Design

5.1 Entity Overview

The database has five tables. MEDICINE is the central entity and contains the most fields. SALES stores one row per transaction and references medicine by the M_NAME field. PURCHASE_ORDERS tracks procurement and references both medicine and supplier by name. COMPANY stores supplier details used by MedicineFrame and PurchaseOrderFrame. AGENTS stores staff credentials and roles used only by the login process.

The current schema uses name-based soft references between tables rather than formal foreign key constraints. This was a deliberate early decision to simplify the first-launch experience: creating a medicine record does not require a supplier record to exist first. The trade-off is that renaming a medicine or supplier can silently orphan related records. Replacing these soft references with proper foreign keys is the second item on the development roadmap in Chapter 9.

Chapter 6

Implementation

6.1 Database Layer

DatabaseHelper is the only class that issues JDBC calls. Its getConnection() method connects to a local MySQL instance on the standard port, loading the MySQL Connector/J driver explicitly:

public static Connection getConnection() throws SQLException {
    String url = "jdbc:mysql://localhost:3306/PharmaDb";
    try {
        Class.forName("com.mysql.cj.jdbc.Driver");
        return DriverManager.getConnection(url, USER, PASS);
    } catch (ClassNotFoundException e) {
        throw new SQLException("MySQL Driver not found", e);
    }
}

initializeDatabase() runs once at startup. CREATE TABLE statements use the IF NOT EXISTS clause so the method is safe to run on every launch: if the table already exists MySQL silently skips the statement. All five tables are declared in full at every startup, and the createDatabaseIfNotExist connection parameter ensures the PharmaDb database itself is created automatically when it does not yet exist. A default Admin account is seeded only when the AGENTS table is empty, covering exactly the first-launch case.

resultSetToTableModel() converts any ResultSet into a Swing DefaultTableModel generically by reading the column count and labels from the result set metadata. Every data table in every frame uses this single method, so adding a column to a table automatically appears in the UI on next launch.

6.2 Authentication and Access Control

The login screen queries the AGENTS table by name and password. On a successful match, the A_ROLE value is extracted and passed as a parameter to DashboardFrame:

String role = Rs.getString("A_ROLE");
new DashboardFrame(role).setVisible(true);

DashboardFrame stores the role and calls applyRolePermissions() immediately after initComponents(). This method disables navigation buttons based on the role, preventing access to restricted modules at the UI level:

private void applyRolePermissions() {
    if ("Technician".equalsIgnoreCase(userRole)) {
        btnAgents.setEnabled(false);
        btnCompany.setEnabled(false);
        btnPO.setEnabled(false);
    } else if ("Pharmacist".equalsIgnoreCase(userRole)) {
        btnAgents.setEnabled(false);
    }
    // Admin: all buttons remain enabled (no action needed)
}
Security vulnerability: The login query is built by string concatenation, which makes it vulnerable to SQL injection. A user entering a crafted string such as ' OR '1'='1' -- as the username would bypass the password check entirely. The fix is a five-line change to use a PreparedStatement. See Chapter 8 for full details.

6.3 Inventory and Billing

MedicineFrame applies a custom DefaultTableCellRenderer that colours each row based on stock and expiry status. The renderer reads the quantity and threshold from the table model and the expiry date from the same row, then sets the background without requiring any user action:

int qty = Integer.parseInt(table.getValueAt(row, 2).toString());
int threshold = Integer.parseInt(table.getValueAt(row, 12).toString());
java.sql.Date expDate = (java.sql.Date) table.getValueAt(row, 4);
long daysToExpiry = (expDate.getTime() - System.currentTimeMillis())
                    / (1000 * 60 * 60 * 24);

if (qty <= threshold) {
    c.setBackground(new Color(255, 204, 204)); // Red: low stock
} else if (daysToExpiry < 30) {
    c.setBackground(new Color(255, 255, 204)); // Yellow: near expiry
} else {
    c.setBackground(Color.WHITE);
}

SellingFrame verifies stock before every sale. If the requested quantity exceeds what is available, it shows an error and makes no database changes. If the sale is valid, it decrements the medicine quantity and writes a SALES row using a PreparedStatement, which correctly prevents injection on this path.

6.4 Purchase Orders and Forecasting

Receiving a purchase order involves two database writes: updating the PO status and incrementing the medicine quantity. Both writes are wrapped in an explicit transaction so they either both succeed or both roll back:

conn.setAutoCommit(false);
try {
    updatePO.executeUpdate();   // SET PO_STATUS = 'Received'
    updateMed.executeUpdate();  // SET M_QUANTITY = M_QUANTITY + qty
    conn.commit();
} catch (SQLException e) {
    conn.rollback();
    throw e;
}

The forecasting calculation sums all units sold in the past 30 days and divides by 30 to get average daily sales. The divisor is always 30, not the number of transactions, so days with no sales are treated as zero. This keeps predictions conservative and avoids recommending unnecessary reorders. The seven-day projection uses Math.ceil so the alert fires before the last unit is sold:

double avgDaily = (double) totalQty / 30.0;
return (int) Math.ceil(avgDaily * 7);

The dashboard shows an alert for any medicine where current stock is less than the seven-day prediction, or below the minimum of 10 units, whichever condition triggers first. Both expiry alerts and stock alerts are loaded every time the dashboard opens, ensuring the information is always current.

Chapter 8

Security Analysis

8.1 Vulnerabilities and Fixes

SQL Injection in Login (Critical). The login query concatenates user-supplied input directly into a SQL string:

String selectQ = "select * from AGENTS where A_NAME='"
    + txtUserName.getText() + "' and A_PASSWORD = '" + pwd + "'";

An attacker entering ' OR '1'='1' -- as the username causes the query to return all rows regardless of the password. Since the code checks Rs.next() to determine login success, the attacker gains access as the first record in the AGENTS table, which is the Admin account. This is an OWASP Top 10 A03 injection vulnerability. The fix is straightforward: replace the concatenated string with a PreparedStatement:

PreparedStatement pstmt = conn.prepareStatement(
    "SELECT * FROM AGENTS WHERE A_NAME = ? AND A_PASSWORD = ?");
pstmt.setString(1, txtUserName.getText());
pstmt.setString(2, new String(l_password.getPassword()));

This change takes under an hour and completely closes the vulnerability. It should be applied before the system is used in any real pharmacy.

Plaintext Password Storage (High). Passwords are stored as plain text in the A_PASSWORD column. Anyone with read access to the MySQL database can recover all credentials immediately. The fix is to hash passwords with BCrypt using the open-source jbcrypt library before storing them, and verify at login with BCrypt.checkpw(). A one-time migration routine should re-hash all existing plaintext passwords on the first upgraded launch.

No Session Timeout (Medium). An authenticated session remains open until the application is closed. An unattended workstation therefore gives full access to whoever sits at it with no re-authentication required. The fix is a javax.swing.Timer that fires after a configurable inactivity period and calls the logout action, returning the user to the login screen.

No Administrative Audit Log (Medium). The SALES table provides a complete log of billing transactions, but there is no record of administrative operations: medicine records deleted, passwords changed, supplier records modified. The fix is an AUDIT_LOG table with columns for timestamp, agent name, action type, table name, and affected record ID, with a row inserted from every CRUD operation via a shared helper method.

Chapter 9

Limitations and Future Work

MySQL dependency (Medium). The application requires a running MySQL instance. Unlike an embedded database, this requires a one-time environment setup. The project includes a Maven configuration to handle all library dependencies automatically, but the MySQL server must be active on the host machine.

Simple Moving Average forecasting accuracy. The SMA model treats all 30 days equally. It does not account for seasonal patterns (for example, antimalarial medicines sell at higher rates during Senegal's rainy season), day-of-week effects, promotions, or supply disruptions. The predictions are conservative and reliable for stable products but will underperform for medicines with variable demand cycles.

No foreign key constraints. Tables reference each other by name string rather than by numeric ID with a formal foreign key. Renaming a medicine or a supplier company does not cascade to SALES or PURCHASE_ORDERS records, which silently breaks the link without any database error being raised. This is the second item on the fix roadmap because it requires a schema migration to add ID-based FK columns to all affected tables.

No prescription management. Prescription-only medicines legally require a valid prescription before dispensing. The system has no mechanism to capture, store, or verify prescription information, which limits its use in any regulated or clinical setting.

Manual data entry only. Every stock entry and every sale requires the pharmacist to type all values. Barcode or QR scanning at the point of sale and at goods receipt would reduce data entry errors and save significant time during high-volume periods.

Chapter 10

Conclusion

The Pharmacy Tracking System delivers on all seven objectives stated at the outset. It manages medicine inventory with full batch information, records every sale and feeds that data into a demand forecasting engine, monitors expiry dates, handles purchase orders with proper transaction guarantees, and enforces role-based access control. It does all of this without requiring a server, a database administrator, or an internet connection, and it installs itself on first launch.

Three technical decisions proved most significant during development. First, centralising all JDBC calls in DatabaseHelper eliminated a large amount of duplicated connection-management code. Second, the transaction-based stock-receiving implementation in PurchaseOrderFrame is the correct engineering approach for any operation that must update more than one table atomically. Third, the migration to MySQL and Maven provides a professional, industry-standard foundation that ensures scalability and ease of deployment.

The security findings are the most urgent items on the development roadmap. The SQL injection vulnerability in the login screen is a five-line fix. The password hashing upgrade is a half-day of work. Both should be applied before this system is deployed in a real pharmacy. The remaining findings (session timeout, audit log) are medium-priority improvements that would be required for any regulated deployment.

With those fixes applied, this system is a practical and complete tool for the community pharmacy context it was designed for: affordable, offline-capable, easy to set up, and covering all the operational tasks that manual records and spreadsheets handle poorly.

public class DatabaseHelper {
    private static final String DB_URL = "jdbc:mysql://localhost:3306/PharmaDb";
    private static final String USER = "root";
    private static final String PASS = "";

    public static Connection getConnection() throws SQLException {
        try {
            Class.forName("com.mysql.cj.jdbc.Driver");
            return DriverManager.getConnection(DB_URL, USER, PASS);
        } catch (ClassNotFoundException e) {
            throw new SQLException("MySQL Driver not found", e);
        }
    }

    public static DefaultTableModel resultSetToTableModel(ResultSet rs) {
        try {
            ResultSetMetaData meta = rs.getMetaData();
            int cols = meta.getColumnCount();
            Vector<String> colNames = new Vector<>();
            for (int i = 1; i <= cols; i++)
                colNames.add(meta.getColumnLabel(i));
            Vector<Vector<Object>> rows = new Vector<>();
            while (rs.next()) {
                Vector<Object> row = new Vector<>();
                for (int i = 1; i <= cols; i++)
                    row.add(rs.getObject(i));
                rows.add(row);
            }
            return new DefaultTableModel(rows, colNames);
        } catch (Exception e) { e.printStackTrace(); return null; }
    }

    public static void initializeDatabase() {
        try (Connection conn = getConnection();
             Statement stmt = conn.createStatement()) {
            // Create MEDICINE - if it already exists, the catch block is a no-op
            try {
                stmt.execute("CREATE TABLE MEDICINE ("
                    + "M_ID INT PRIMARY KEY, M_NAME VARCHAR(50), "
                    + "M_QUANTITY INT, M_PRICE DOUBLE, "
                    + "M_EXPDATE DATE, M_MFTDATE DATE, "
                    + "M_COMPANY VARCHAR(50), "
                    + "M_OWNER VARCHAR(50) DEFAULT 'Main', "
                    + "M_CATEGORY VARCHAR(50), M_STRENGTH VARCHAR(20), "
                    + "M_DOSAGE VARCHAR(50), M_UNIT_COST DOUBLE, "
                    + "M_THRESHOLD INT DEFAULT 10, M_BATCH VARCHAR(50))");
            } catch (SQLException e) { /* table exists, continue */ }
            // AGENTS, SALES, PURCHASE_ORDERS, COMPANY created the same way ...
            // Seed default admin on first launch
            try (ResultSet rs = stmt.executeQuery(
                    "SELECT COUNT(*) FROM AGENTS")) {
                if (rs.next() && rs.getInt(1) == 0) {
                    stmt.execute("INSERT INTO AGENTS VALUES "
                        + "(1,'Admin',30,'admin123','0000000000',"
                        + "'Other','admin@pharma.com','Admin')");
                }
            }
        } catch (SQLException e) { e.printStackTrace(); }
    }
}

public class ForecastingHelper {

    public static int predictDemand(String medicineName) {
        int totalQty = 0, count = 0;
        try (Connection conn = DatabaseHelper.getConnection();
             PreparedStatement pstmt = conn.prepareStatement(
                 "SELECT S_QTY FROM SALES "
                 + "WHERE S_MED_NAME = ? AND S_DATE >= ?")) {
            LocalDate ago = LocalDate.now().minusDays(30);
            pstmt.setString(1, medicineName);
            pstmt.setDate(2, java.sql.Date.valueOf(ago));
            try (ResultSet rs = pstmt.executeQuery()) {
                while (rs.next()) {
                    totalQty += rs.getInt("S_QTY");
                    count++;
                }
            }
            if (count == 0) return 0;
            // Divide by 30 (window), not count, so zero-sale days are averaged in
            return (int) Math.ceil((double) totalQty / 30.0 * 7);
        } catch (SQLException e) { e.printStackTrace(); return 0; }
    }

    public static List<String> getLowStockAlerts() {
        List<String> alerts = new ArrayList<>();
        try (Connection conn = DatabaseHelper.getConnection();
             Statement stmt = conn.createStatement();
             ResultSet rs = stmt.executeQuery(
                 "SELECT M_NAME, M_QUANTITY FROM MEDICINE")) {
            while (rs.next()) {
                String name = rs.getString("M_NAME");
                int qty   = rs.getInt("M_QUANTITY");
                int pred  = predictDemand(name);
                if (qty < pred || qty < 10)
                    alerts.add(name + "  (stock: " + qty
                        + ", 7-day forecast: " + pred + ")");
            }
        } catch (SQLException e) { e.printStackTrace(); }
        return alerts;
    }

    public static List<String> getExpirationAlerts() {
        List<String> alerts = new ArrayList<>();
        try (Connection conn = DatabaseHelper.getConnection();
             Statement stmt = conn.createStatement();
             ResultSet rs = stmt.executeQuery(
                 "SELECT M_NAME, M_EXPDATE FROM MEDICINE")) {
            LocalDate limit = LocalDate.now().plusDays(30);
            while (rs.next()) {
                java.sql.Date d = rs.getDate("M_EXPDATE");
                if (d != null && d.toLocalDate().isBefore(limit))
                    alerts.add("EXPIRY: " + rs.getString("M_NAME")
                        + "  (expires: " + d.toLocalDate() + ")");
            }
        } catch (SQLException e) { e.printStackTrace(); }
        return alerts;
    }

    public static double getInventoryValue() {
        double total = 0;
        try (Connection conn = DatabaseHelper.getConnection();
             Statement stmt = conn.createStatement();
             ResultSet rs = stmt.executeQuery(
                 "SELECT M_QUANTITY, M_UNIT_COST FROM MEDICINE")) {
            while (rs.next())
                total += rs.getInt("M_QUANTITY") * rs.getDouble("M_UNIT_COST");
        } catch (SQLException e) { e.printStackTrace(); }
        return total;
    }
}
